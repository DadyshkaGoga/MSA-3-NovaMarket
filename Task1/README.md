## Архитектурные решения

**Декомпозиция (database-per-service).** Девять микросервисов в границе NovaMarket плюс брокер
Kafka. Каждый сервис владеет своими данными (в подписи контейнера указан его store —
PostgreSQL/Redis), чтобы убрать связность по БД и дать независимое масштабирование. Внешние
системы — платёжный шлюз и логистический провайдер — за явными адаптерами (Payment/Delivery).

- **Catalog** — каталог, цены, карточки, фильтры; наличие актуализирует, потребляя `StockChanged`.
- **Cart** — корзина; при оформлении публикует `CartCheckedOut`.
- **Order** — агрегат заказа, инициатор Saga, источник статуса для личного кабинета.
- **Inventory** — резервирование и остатки склада.
- **Payment** — оплата, токенизация карты, возвраты (внешний шлюз).
- **Delivery** — заявка на доставку, трек-номер (внешний логист).
- **Notification / Seller / Review** — уведомления, кабинет продавца, отзывы.

**Вариант отрисовки потоков событий — №1 (broker-centric).** Брокер показан явно, потому что
один тип события потребляют несколько сервисов (fan-out): `PaymentSucceeded` → Delivery + Order +
Notification; `OrderCreated` → Inventory + Notification + Seller. Это честнее отражает EDA, чем
прямые стрелки «сервис → сервис», и упрощает добавление новых потребителей по подписке (требование
бизнеса о лёгком подключении сервисов аналитики/антифрода).

**Saga — хореография.** Оформление заказа реализовано без центрального оркестратора: каждый сервис
реагирует на событие предыдущего шага и публикует следующее; при отказе запускаются компенсации в
обратном порядке. Это даёт слабую связность и устойчивость к локальным отказам. Детальный реестр
событий (`domain` / `failure` / `compensation`) и компенсационная матрица — в
[saga-events.md](./saga-events.md).

**Соответствие NFR отклика (≤1 c в 99,99%, 0,3 c в 98%).** Пользовательские действия (каталог,
корзина, оформление, статус) обслуживаются синхронно и быстро; тяжёлая распределённая работа
(резерв → оплата → доставка) вынесена в асинхронную Saga за брокером, поэтому отклик на действие
покупателя не ждёт завершения всей транзакции.

## Как воспроизвести (рендер диаграмм)

```bash
cd MSA-3-NovaMarket
docker run --rm -v "$PWD/Task1:/work" -w /work plantuml/plantuml -tpng "*.puml"
```

Диаграммы используют C4-PlantUML из stdlib (для C2) и стандартный UML Sequence. PNG приложены в
этой папке.

## Замечания

- Семантика доставки и идемпотентность зафиксированы в [saga-events.md](./saga-events.md)
  (at-least-once + идемпотентность по `orderId`; Transactional Outbox как прод-апгрейд — обозначен,
  не реализуется в рамках задания-дизайна).
- БД отдельных «вспомогательных» сервисов (Notification/Seller/Review) не вынесены отдельными
  узлами на C2, чтобы не перегружать схему; принцип database-per-service указан в подписи каждого
  сервиса.
