# ADR-001: Паттерн получения агрегированных данных для сценария «История заказов»

## Status

Accepted — 2026-06-29, автор: Черкасов Фёдор. Спринт 3, NovaMarket.
Связан с [Task1](../Task1/README.md) (событийная архитектура и Saga оформления заказа — источник
доменных событий, которыми наполняется read-model).

## Context and Problem Statement

После доставки покупатель открывает в личном кабинете **историю покупок**: список всех заказов
(стоимость, дата, способ доставки) и детальную карточку каждого заказа (состав, количество, цена,
итоговая сумма, способ оплаты и доставки, финальный статус), а также действия — скачать чек,
оставить отзыв, заказать снова.

Данные для одного заказа физически разнесены по нескольким сервисам (Order, Inventory/каталожные
позиции, Payment, Delivery — см. C2 в [Task1](../Task1/c2-eda.png)). Сценарий **чтение-тяжёлый**
(история открывается часто, в т.ч. с ростом до 40 000+ заказов/день) и должен укладываться в общий
NFR отклика. Нужно выбрать паттерн агрегации: **API Composition**, **CQRS** или **Event Sourcing**
(либо их комбинацию).

Архитектурно значимые требования:

| Шифр | Требование | Влияние на архитектуру |
|------|------------|------------------------|
| NFR-01 | Отклик ≤ 1 c в 99,99%; 0,3 c в 98% | Чтение истории — один быстрый источник, без read-time fan-out |
| F-01 | Список заказов пользователя + детальная карточка | Денормализованная проекция «заказ целиком» |
| F-02 | Скачать чек, оставить отзыв, повторить заказ | Ссылки на Payment (чек) / Review / Order (reorder) |
| P-01 | Read-heavy масштабирование до 40k+ заказов/день | Независимо масштабируемое хранилище чтения |
| R-01 | История доступна даже при недоступности write-сервисов | Развязка чтения от write-пути |
| C-01 | EDA уже эмитит доменные события (Task1) | Переиспользовать существующий поток событий |

## Decision Drivers

1. Соблюдение NFR отклика под нагрузкой (**gate**): чтение истории не должно зависеть от
   синхронного опроса нескольких сервисов.
2. Независимое масштабирование чтения (read-heavy сценарий).
3. Развязка чтения от доступности и схемы write-сервисов.
4. Переиспользование уже существующего потока доменных событий (Task1), минимум нового кода.
5. Разумная сложность для MVP, допустимая eventual consistency (история — постфактум).

## Considered Options

### Вариант 1. API Composition
API-композитор (BFF/шлюз) в момент запроса синхронно вызывает Order, Payment, Delivery (и др.) и
склеивает ответ. Отдельного хранилища нет.

### Вариант 2. CQRS — денормализованный read-model
Выделенный **Order History Service** держит денормализованную проекцию «заказ целиком» в
read-optimized БД. Проекция наполняется потреблением доменных событий, которые система уже
публикует: `OrderCreated`, `PaymentSucceeded`, `DeliveryScheduled`, `OrderDelivered`,
`OrderCancelled`. Чтение истории — один быстрый запрос к проекции. См.
[c2-eda-history.puml](./c2-eda-history.png).

### Вариант 3. Event Sourcing
Состояние заказа хранится как лог событий — источник истины; представление истории
восстанавливается реплеем событий (на практике — через ES-проекции). Меняет и **write**-модель:
сервисы становятся event-sourced.

## Decision Outcome

**Выбран Вариант 2 — CQRS (денормализованный read-model, наполняемый доменными событиями).**

Это единственный вариант, проходящий gate по NFR-01: чтение истории — один запрос к
денормализованной проекции, без read-time fan-out, с независимым масштабированием под read-heavy
нагрузку. CQRS естественно ложится на уже существующий событийный поток (Task1): read-model — ещё
один потребитель тех же топиков, новых требований к write-сервисам нет. История остаётся доступной,
даже если часть write-сервисов недоступна (R-01).

### Weighted Decision Matrix

Оценка 1–5 (больше — лучше). **K-01 — gate-критерий**: оценка ≤ 2/5 дисквалифицирует вариант
независимо от взвешенной суммы.

| Критерий | Вес | В1 API Comp. | Вклад В1 | В2 CQRS | Вклад В2 | В3 Event Sourcing | Вклад В3 |
|---|:-:|:-:|:-:|:-:|:-:|:-:|:-:|
| K-01 Соответствие NFR-01 (отклик), **gate** | 25% | 2 | 0.50 | 5 | **1.25** | 2 | 0.50 |
| K-02 Масштабируемость чтения (40k/день) | 20% | 2 | 0.40 | 5 | **1.00** | 3 | 0.60 |
| K-03 Развязка от write-сервисов | 15% | 2 | 0.30 | 5 | **0.75** | 4 | 0.60 |
| K-04 Простота реализации для MVP | 15% | 5 | **0.75** | 3 | 0.45 | 1 | 0.15 |
| K-05 Совместимость с потоком событий EDA | 15% | 2 | 0.30 | 5 | **0.75** | 3 | 0.45 |
| K-06 Допустимость eventual consistency | 10% | 5 | **0.50** | 4 | 0.40 | 4 | 0.40 |
| **ИТОГО** | **100%** | | **2.75** | | **4.60** | | **2.70** |

**Победитель — Вариант 2 (CQRS)** с разрывом **+1.85** к ближайшему. Варианты 1 и 3 **проваливают
gate K-01** (оценка 2/5 по отклику), поэтому отклоняются даже без учёта суммы.

### Анализ чувствительности

- Удвоить вес K-04 (простота MVP) в пользу API Composition — CQRS всё равно лидирует за счёт
  K-01/K-02/K-03/K-05 и непройденного gate у конкурентов.
- Обнулить gate и считать только сумму — CQRS (4.60) сохраняет отрыв. Решение устойчиво.

## Pros and Cons of the Options

### Вариант 2 — CQRS (выбранный)
**Pros**
- Чтение — один денормализованный запрос → держит p98 0,3 c / p99.99 ≤ 1 c.
- Независимое масштабирование read-store под read-heavy нагрузку.
- Развязка от write-сервисов; история доступна при их частичной недоступности.
- Переиспользует существующие доменные события — минимум нового кода в write-сервисах.

**Cons**
- Eventual consistency (задержка проекции — секунды); требуется идемпотентная проекция и обработка
  out-of-order событий.
- Дополнительный сервис и хранилище (дублирование данных) — операционная стоимость.

### Вариант 1 — API Composition
**Pros**: проще всего для MVP; данные всегда «живые» (strong read-after-write).
**Cons**: latency = сумма/макс синхронных вызовов + сеть → риск нарушить NFR под нагрузкой;
амплификация нагрузки на write-сервисы; жёсткая связность чтения с их доступностью.

### Вариант 3 — Event Sourcing
**Pros**: полная история изменений и аудит; гибкие проекции.
**Cons**: переусложнение для MVP (event store, версионирование, снапшоты, ребилды); требует менять
и write-модель; без CQRS-проекций чтение медленное.

## Compromises (компромиссы выбранного решения)

1. **Eventual consistency.** Принимаем секундную задержку проекции — для постфактумной истории это
   приемлемо. Митигация: проекция идемпотентна по `orderId`+тип события, обрабатывает повторы и
   нарушения порядка; критичный «живой» статус заказа покупатель видит в Order Service, а не в
   истории.
2. **Дублирование данных** в read-store. Принимаем как осознанную цену CQRS. Митигация: проекцию
   можно **перестроить из лога событий** (ES-lite), сохраняя ретенцию топиков — это снимает риск
   рассинхронизации без перехода на полный Event Sourcing.
3. **Чек и отзыв** — не дублируем в проекцию: history отдаёт ссылку, файл чека берётся из Payment,
   создание отзыва идёт в Review (точечная API Composition для редких действий).

## Constraints, Limitations, Risks

| Категория | Описание | Митигация |
|---|---|---|
| **Риск** | Рассинхронизация проекции при сбое потребителя | Идемпотентность + перестроение проекции из лога событий |
| **Риск** | Out-of-order доставка событий ломает статус в проекции | Версия/таймстемп события, монотонное применение по `orderId` |
| **Ограничение** | Read-after-write «секунды» — история не мгновенна | Живой статус — в Order Service; история — постфактум |
| **Ограничение** | Доп. инфраструктура (сервис + БД) | Оправдано read-heavy масштабом и NFR |
